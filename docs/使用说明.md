# Build Workflow 构建流程

## 概述

基于 GitHub Actions 的 ImmortalWrt 24.10.6 x86_64 固件自动构建。核心原则：

- **ImmortalWrt 系统自带包**（DEFAULT_PACKAGES）→ 源码编译
- **所有第三方包** → 从 feed/GitHub 下载预编译 ipk，首次启动 `opkg install`
- **缓存**：dl 缓存下载好的源码包，ccache 缓存编译产物

---

## GitHub Actions 工作流（`.github/workflows/build.yml`）

### 步骤顺序

```
1. Prepare environment    # 安装依赖、释放磁盘
2. Checkout               # 检出 builder 仓库
3. Clone source code      # git clone ImmortalWrt v24.10.6
4. Get date for dl cache  # 用于 dl 缓存 key（每天一份）
5. Restore dl cache        # 恢复下载缓存到 /workdir/openwrt/dl/
6. Get date for ccache key
7. Configure feeds        # diy-part1.sh（config-manifest → generate-provides → ln -sf → feeds update/install）
8. Install feeds          # feeds install -a（diy-part1.sh 已内置，此步冗余但无害）
9. Apply custom config    # diy-part2.sh（P0 防御 + strict config-manifest 加载）
10. Restore ccache         # actions/cache@v5（自动恢复 + job 结束自动保存）
11. Download sources       # make download -j$(nproc)
12. Save dl cache          # 成功/失败分别保存（带日期 key）
13. Compile firmware       # chown/chmod ccache → ccache -z/M/s → make -j$(nproc) V=s
14. ccache stats           # ccache -s + 超 6GB 清理
15. Save ccache on failure # 构建失败时保存失败缓存
16. Verify binary inject   # 检查 binary-manifest.json 的 skipped 包
17. Release firmware       # 上传 img.gz + sysupgrade.bin.gz，保留 3 个
```

## 缓存策略

### dl 缓存（源码包缓存）

```yaml
# 获取日期（与 ccache 一致）
- name: Get date for dl cache key
  id: dl-date
  run: echo "date=$(/bin/date -u "+%Y%m%d")" >> "$GITHUB_OUTPUT"

# 恢复缓存（key 含日期，每天一份，前缀回退到最近一天）
- name: Restore dl cache
  uses: actions/cache/restore@v5
  with:
    path: /workdir/openwrt/dl/
    key: dl-${{ env.REPO_BRANCH }}-${{ steps.dl-date.outputs.date }}-${{ hashFiles('feeds.conf.default', 'diy-part1.sh') }}
    restore-keys: |
      dl-${{ env.REPO_BRANCH }}-${{ steps.dl-date.outputs.date }}-
      dl-${{ env.REPO_BRANCH }}-

# 构建成功时保存（key 含日期，每天可写入一条新缓存）
- name: Save dl cache on success
  if: success()
  uses: actions/cache/save@v5
  with:
    path: /workdir/openwrt/dl/
    key: dl-${{ env.REPO_BRANCH }}-${{ steps.dl-date.outputs.date }}-${{ hashFiles('feeds.conf.default', 'diy-part1.sh') }}

# 构建失败时保存（带 -failed- 后缀，不冲突）
- name: Save dl cache on failure
  if: failure()
  uses: actions/cache/save@v5
  with:
    path: /workdir/openwrt/dl/
    key: dl-${{ env.REPO_BRANCH }}-${{ steps.dl-date.outputs.date }}-${{ hashFiles('feeds.conf.default', 'diy-part1.sh') }}-failed-${{ github.run_number }}
```

- **key 含日期 + feeds 配置哈希**，每天一份新缓存，日切时 key 变化自动写入新条目，旧缓存被 GitHub 自动驱逐（限额 10GB）
- 恢复时先精确匹配当天 key，再用日期前缀回退到最近一天，总能找到有效缓存

### ccache 缓存（编译缓存）

```yaml
# key 含日期 + feeds 哈希，每天一份 + 变更感知
# actions/cache@v5 单 action 自动恢复+保存（key 不存在时 job 结束自动保存）
- name: Get date for ccache key
  id: ccache-date
  run: echo "date=$(/bin/date -u "+%Y%m%d")" >> "$GITHUB_OUTPUT"

- name: ccache cache
  uses: actions/cache@v5
  with:
    path: /home/runner/.ccache
    key: ccache-${{ env.REPO_BRANCH }}-${{ steps.ccache-date.outputs.date }}-${{ hashFiles('feeds.conf.default', 'diy-part1.sh') }}
    restore-keys: |
      ccache-${{ env.REPO_BRANCH }}-${{ steps.ccache-date.outputs.date }}-
      ccache-${{ env.REPO_BRANCH }}-

# 构建失败时单独保存（带 -failed-{run_number} 后缀，避免与成功缓存冲突）
- name: Save ccache on failure
  if: failure()
  uses: actions/cache/save@v5
  with:
    path: /home/runner/.ccache
    key: ccache-${{ env.REPO_BRANCH }}-${{ steps.ccache-date.outputs.date }}-${{ hashFiles('feeds.conf.default', 'diy-part1.sh') }}-failed-${{ github.run_number }}
```

**ccache 三层保护机制：**

1. **diy-part2.sh 开头** export `CCACHE_DIR` + `CCACHE_MAXSIZE="5G"` + `CCACHE_COMPRESS="true"`
2. **make defconfig 之前** `./scripts/kconfig-tool --set-str CCACHE_DIR "/home/runner/.ccache"` 写入 .config
3. **make defconfig 之后** 强制 `--enable CCACHE` + `--set-str CCACHE_DIR`，防止 Kconfig 重置为空

OpenWrt 的 `rules.mk` 会 export `CCACHE_DIR:=$(CONFIG_CCACHE_DIR)`，如果 .config 中该值为空，export 为空字符串，ccache 回退到 `~/.cache/ccache`，与 cache action 保存的 `/home/runner/.ccache` 不匹配。三层保护确保路径始终一致。

**编译步骤**中增加：`chown/chmod` 确保写权限 + `ccache -z` 重置统计 + `ccache -M 5G` 限容 + `ccache -s` 打印状态。

**diy-part2.sh 末尾**输出 CCACHE DEBUG 块，打印环境变量、.config 值和 ccache 目录状态。

构建完后有 ccache stats 步骤输出统计 + 超 6GB 自动清理。

## 32 位应用支持

### 架构
- 内核 `CONFIG_IA32_EMULATION=y`（x86 + x86_64 config-6.6 均已打补丁）
- 预置 `musl 32-bit`（`/lib/ld-musl-i386.so.1` + `/lib32/*.so`）和 `glibc 32-bit`（`/lib/ld-linux.so.2` + `/lib32/glibc/*.so`）双运行时
- 提供 `run-i386` 包装脚本，自动识别 musl/glibc 二进制并设置正确的 `LD_LIBRARY_PATH`

### gh-bin 兼容性检查策略
`check_gh_binary_deps()` 在提取 gh-bin 二进制后自动执行：

| 架构 | 链接方式 | 结果 |
|------|---------|------|
| x86-64 | 静态 | ✅ 直接可用 |
| x86-64 | musl 动态 | ✅ 直接可用 |
| x86-64 | glibc 动态 | ❌ 阻断（musl 环境无法运行 64-bit glibc） |
| i386 (32-bit) | 静态 | ✅ 直接可用 |
| i386 (32-bit) | musl 动态 | ✅ musl32 runtime 兜底 |
| i386 (32-bit) | glibc 动态 | ✅ glibc32 runtime 兜底（不阻断） |

### 运行时维护
构建时自动执行 `runtime-musl32.sh` 和 `runtime-glibc32.sh`，从 `runtime/*.tar.gz` 解压到 `files/` 目录，最终打包进固件 rootfs。

升级 ImmortalWrt 版本时需要重新生成 tarball：
- `runtime/musl32.tar.gz` — 从新版本 i386 rootfs 提取
- `runtime/glibc32.tar.gz` — 从 Ubuntu 22.04 i386 环境提取
- 或在 CI 中运行 `scripts/build-runtime-tarballs.sh` 自动生成

### 维护注意事项
- 32 位库与内核版本弱相关（取决于 musl/libc ABI），跨小版本升级通常兼容
- 升级大版本（如 24.10 → 25.x）时**必须**重新生成 tarball，否则 32 位程序可能因 musl/glibc ABI 不兼容而崩溃
- `files/usr/bin/run-i386` 脚本无需随版本更新，除非 musl/glibc 的 ld 路径发生变化

## 第三方包处理架构

### 核心文件

| 文件 | 作用 |
|------|------|
| `scripts/config-manifest.sh` | 声明 BINARY_SOURCE（每包的下载来源）和包清单 |
| `scripts/manifest-lib.sh` | `apply_manifest()` 写入 .config（内部调用 `./scripts/kconfig-tool` 而非 OpenWrt 的 `scripts/config/`） |
| `shell/prepare-binary.sh` | 下载 ipk 到 `files/etc/ipk-cache/`，生成 uci-defaults 脚本 |
| `scripts/kernel-config.sh` | 内核配置补丁（IA32_EMULATION + 预设内核选项 + 委托 kernel-config-patch.py 注入 olddefconfig） |
| `scripts/kernel-config-patch.py` | 独立 Python 脚本，在 include/kernel-defaults.mk 中注入 $(KERNEL_MAKE) olddefconfig |
| `scripts/kconfig-tool` | [运行时] 从 Linux 内核官方下载的 `scripts/config`，重命名后替代 OpenWrt 的 `scripts/config/` 目录 |
| `diy-part1.sh` | 前置编排器：P0 环境变量检查 → source config-manifest + generate-provides → ln -sf → feeds update/install |
| `diy-part2.sh` | 主编排器：P0 环境变量检查 → export CCACHE → chmod 脚本 → kernel-config/runtime → 下载 kconfig-tool → make defconfig → CCACHE 三层保护 → strict config-manifest + apply_manifest (via kconfig-tool) → prepare-binary → 校验 → CCACHE DEBUG |
| `package/custom-provides/Makefile` | [自动生成] PROVIDES 虚拟包，由 generate-provides.sh 动态生成，接管所有 BINARY 包的依赖请求（严禁手动修改） |
| `scripts/binary-packages.sh` | BINARY 包扁平列表，被 diy-part1/diy-part2 共用 |
| `scripts/verify-kernel-deps.sh` | 校验 BINARY 包的内核依赖 (.config 启用检查) |
| `scripts/verify-pkg-consistency.sh` | 校验 BINARY 包一致性 (LuCI 配对 + 运行时依赖闭环) |
| `scripts/generate-provides.sh` | 动态生成 PROVIDES 虚拟包 Makefile (替代手动维护) |
| `scripts/sort-ipk-deps.py` | IPK 依赖拓扑排序 (Kahn 算法 → install_order.list) |
| `files/etc/sysupgrade.conf` | sysupgrade 保留安装日志路径 |

### 包分类

```
BINARY（第三方包，不编译，开机装 ipk）
├── feed:luci       — USTC 镜像 /releases/24.10.6/packages/x86_64/luci/
├── feed:packages   — USTC 镜像 /releases/24.10.6/packages/x86_64/packages/
├── feed:base       — USTC 镜像 /releases/24.10.6/packages/x86_64/base/
├── gh:owner/repo   — GitHub Releases（ipk 匹配）
└── gh-bin:         — GitHub Releases（tar.gz 提取 ELF 到 files/）

SOURCE（显式启用源码编译的包，很少用）
└─ 仅用于需要在 .config 中 =y 但不属于 DEFAULT_PACKAGES 的 feed 包

EXCLUDE（禁用，不编译不安装）
└─ 存在冲突或有问题的包（如 luci-app-fchomo）
```

### manifest-lib.sh 的 apply_manifest()

```
BINARY 包 → ./scripts/kconfig-tool --disable → make 跳过编译
EXCLUDE 包 → ./scripts/kconfig-tool --disable → make 跳过编译
SOURCE 包 → ./scripts/kconfig-tool --enable → make 正常编译
```

使用 Linux 内核官方的 `scripts/config` 脚本（重命名为 `kconfig-tool`，避免与 OpenWrt 的 `scripts/config/` 目录冲突）。同时自动启用 `CONFIG_PACKAGE_custom-binary-provides`（编译空包，PROVIDES 所有 BINARY 包），编译期依赖系统认为 BINARY 包已存在，避免 `depends on` 导致的编译中断。

调用时机：必须在 make defconfig 之后执行，且之后绝不再执行 make defconfig。否则 Kconfig 引擎会根据 depends on/select 关系把 BINARY 包复活。

## 数据流

### 编译阶段（Apply custom config）

```
config-manifest.sh
  ├─ 声明 BINARY_SOURCE[smartdns]="feed:packages"
  ├─ BINARY 清单 = smartdns luci-app-openclash docker ...
  └─ apply_manifest()  →  写入 .config（禁用所有 BINARY 包）

diy-part1.sh（P0 防御：GITHUB_WORKSPACE 检查）
  → source config-manifest.sh + generate-provides.sh（动态生成 PROVIDES Makefile）⚠️ 必须在 feeds install 前
  → ./scripts/feeds update -a / install -a（建立包含完整 PROVIDES 的索引）

diy-part2.sh（P0 防御：GITHUB_WORKSPACE 检查 + strict config-manifest 加载）
  → export CCACHE_DIR/MAXSIZE/COMPRESS + chmod +x scripts/*.sh
  → kernel-config/runtime patches（IA32_EMULATION + olddefconfig via kernel-config-patch.py）
  → 下载 Linux 官方 scripts/config 为 kconfig-tool
  → ./scripts/kconfig-tool --set-str CCACHE_DIR（defconfig 前注入）
  → make defconfig（OpenWrt 计算 Kconfig 依赖）
  → 【关键修复】--enable CCACHE + --set-str CCACHE_DIR（防止 Kconfig 重置）
  → strict source config-manifest.sh（含失败中断 + 空值安全默认 + 包数量日志）
  → apply_manifest()  via kconfig-tool
      ├─ ./scripts/kconfig-tool --disable（BINARY 包）
      ├─ ./scripts/kconfig-tool --enable（SOURCE 包）
      └─ ./scripts/kconfig-tool --enable CONFIG_PACKAGE_custom-binary-provides
  → CCACHE DEBUG（打印环境变量、.config 值、ccache -s）
  → prepare-binary.sh
      ├─ feed:packages smartdns → download_feed_pkg()
      │   └─ curl USTC 镜像 Packages.gz
      │   └─ awk 精确匹配 $1=="Package:" && $2==pkg，提取 Filename
      │   └─ 下载 smartdns_*.ipk → files/etc/ipk-cache/
      ├─ gh:vernesong/OpenClash → download_gh_release()
      │   └─ GitHub API → 下载 luci-app-openclash_*.ipk → files/etc/ipk-cache/
      ├─ gh-bin: → download_gh_binary()
      └─ 生成 uci-defaults/99-install-ipk-cache.sh
  → verify-kernel-deps.sh（校验 ipk 中 kmod 依赖 + BINARY_KERNEL_DEPS 声明式依赖）
  → verify-pkg-consistency.sh（校验 LuCI 配对 + 运行时依赖闭环）

gh-bin 包的二进制兼容性检查：`check_gh_binary_deps()` 自动验证 ELF 架构（允许 x86-64 和 i386）、链接方式（仅阻断 x86-64 glibc，i386 交由兼容层兜底）、列出 NEEDED 共享库，确保提取的二进制能在 ImmortalWrt 64/32 位混合环境下运行。
```

【关键】apply_manifest 必须在 make defconfig 之后执行，且之后绝不再执行 make defconfig。

### 首次启动阶段（uci-defaults）

```
99-install-ipk-cache.sh  ← uci-defaults 框架自动执行
  ├─ 批量安装：优先使用 install_order.list（DAG）, 降级为前缀分层排序 (core → luci-app → luci-theme → luci-i18n)
  └─ 日志 /etc/config/ipk-install.log
```

## 维护注意事项

### 1. 新增第三方包

新增 BINARY 包需要修改两个文件：`scripts/config-manifest.sh` 和 `scripts/binary-packages.sh`。

#### 1.1 声明下载源

在 `scripts/config-manifest.sh` 的 BINARY_SOURCE 区域新增一行：

```bash
# 从 ImmortalWrt USTC 镜像下载预编译 ipk
BINARY_SOURCE[包名]="feed:{luci|packages|base}"

# 从 GitHub Releases 下载 ipk
BINARY_SOURCE[包名]="gh:owner/repo"           # 最新 Release
BINARY_SOURCE[包名]="gh:owner/repo:tag"        # 锁定版本

# 从 GitHub Releases 下载 tar.gz 提取 ELF 到 files/
BINARY_SOURCE[包名]="gh-bin:owner/repo:pattern_regex:target_dir"
```

示例：
```bash
BINARY_SOURCE[luci-app-mypackage]="feed:luci"
```

#### 1.2 加入 BINARY 清单

在同一文件的 BINARY 清单区域（`# ==================== BINARY 包清单 ====================` 之后），追加包名：

```bash
CONFIG_MANIFEST_BINARY="$CONFIG_MANIFEST_BINARY luci-app-mypackage luci-i18n-mypackage-zh-cn"
```

然后同步更新 `scripts/binary-packages.sh` 的 `BINARY_PACKAGES_FLAT` 列表（格式相同，各包名空格分隔）。

#### 1.3 处理 PROVIDES（无需手动操作）

`generate-provides.sh` 会在 diy-part1.sh 阶段自动从 BINARY 清单生成对应的 PROVIDES，
同时会扫描 `package/feeds/` 中官方已声明 PROVIDES 的包并自动过滤，避免重复冲突。

**严禁手动编辑** `package/custom-provides/Makefile`，该文件由脚本动态生成，每次构建会被覆盖。

#### 1.4 LuCI 配对规则

如果包有 LuCI 界面（形如 `luci-app-xxx` 或 `luci-i18n-xxx-zh-cn`），确保核心包也在清单中。
系统提供防呆检查（`BINARY_LUCI_MANDATORY` 声明在 config-manifest.sh 末尾），
装了核心包没装界面包会报错。若新包有 LuCI 界面，在 `BINARY_LUCI_MANDATORY` 数组中追加核心包名。

#### 1.5 内核依赖（可选）

如果包需要特定内核模块（如 Docker 需要 VETH），在 `BINARY_KERNEL_DEPS` 中声明：

```bash
BINARY_KERNEL_DEPS[包名]="CONFIG_VETH CONFIG_NETFILTER_XT_MATCH_ADDRTYPE"
```

构建时会自动校验这些 .config 选项是否已启用。

#### 1.6 排除不需要的包

如需彻底禁用一个包（不编译、不安装、不进清单），加到 EXCLUDE 区域：

```bash
CONFIG_MANIFEST_EXCLUDE="$CONFIG_MANIFEST_EXCLUDE 包名"
```

#### 操作示例：新增 luci-app-mypackage（feed 源）

```
1. config-manifest.sh 中：
     BINARY_SOURCE[luci-app-mypackage]="feed:luci"
     BINARY_SOURCE[luci-i18n-mypackage-zh-cn]="feed:luci"

2. config-manifest.sh BINARY 清单追加：
     CONFIG_MANIFEST_BINARY="$CONFIG_MANIFEST_BINARY luci-app-mypackage luci-i18n-mypackage-zh-cn"

3. binary-packages.sh BINARY_PACKAGES_FLAT 追加相同包名

4. 如有内核依赖，加 BINARY_KERNEL_DEPS[luci-app-mypackage]="CONFIG_XXX"

5. 如该包有 LuCI 界面，加 "mypackage" 到 BINARY_LUCI_MANDATORY
```

### 2. ln -sf 链接不可删除

`diy-part1.sh` 中的 `ln -sf` 步骤（将 `$GITHUB_WORKSPACE/package/custom-provides` 链接到 openwrt 源码树）**绝不可删除**。
feeds 扫描时只会索引 `package/` 目录下的内容，没有此链接，PROVIDES 虚拟包不会被索引到，依赖解析会找不到 PROVIDES 声明。

### 3. 绝对不要在 apply_manifest 之后执行 make defconfig

`apply_manifest()` 使用 `./scripts/kconfig-tool --disable` 禁用了所有 BINARY 包。
如果之后再执行 `make defconfig`，Kconfig 引擎会根据 `depends on`/`select` 关系把这些禁用的包重新启用（"复活"），
导致这些包被编译，与"开机装 ipk"的意图冲突。

**正确顺序：**
```
make defconfig → (kconfig-tool 加固 CCACHE) → apply_manifest (via kconfig-tool) → (绝不再 defconfig)
```

### 4. 缓存路径硬编码不可改

`build.yml` 中 `actions/cache` 的 `path: /home/runner/.ccache` 和 `diy-part2.sh` 中注入 `.config` 的 `CONFIG_CCACHE_DIR="/home/runner/.ccache"` **均不可改用 `~` 或 `$HOME`**。原因：

- GitHub `actions/cache` 的 key 计算包含 path 字面值，用 `~` 会导致缓存版本计算不一致，旧缓存全部失效
- OpenWrt 的 `rules.mk` 会 export `CCACHE_DIR:=$(CONFIG_CCACHE_DIR)`，如果 `.config` 中该值为空，export 为空字符串，ccache 回退到 XDG 默认 `~/.cache/ccache`，与 cache action 保存的 `/home/runner/.ccache` 不匹配，缓存永不命中
- `$HOME` 在 GitHub Actions runner 上固定为 `/home/runner`，硬编码等价但更安全（避免 shell 展开歧义）

## 常见问题

### 为什么 feed 包也要开机装 ipk，不编译？

编译每个包需要 1-10 分钟不等，OpenWrt 有约 5000 个包选项，全编译要 4+ 小时。预编译 ipk 直接从 ImmortalWrt 官方 USTC 镜像下载，秒级完成。

### 开机装 ipk 依赖怎么处理？

`opkg install --force-depends` 跳过依赖检查。运行时所需的依赖包是 ImmortalWrt 系统自带（DEFAULT_PACKAGES）编译进固件的，已经在 opkg 数据库中有记录。

### 如果某个第三方包在 USTC 镜像上找不到？

`download_feed_pkg` 找不到该包 → `PKG_STATUS[包名]="skipped"` → `binary-manifest.json` 记录跳过 → 构建日志和 Release notes 会列出跳过的包。

### ccache 为什么之前不生效？

OpenWrt 的 `rules.mk` 中 `export CCACHE_DIR:=$(CONFIG_CCACHE_DIR)` 覆盖了 GitHub Actions 设置的 `CCACHE_DIR` 环境变量。`.config` 中 `CONFIG_CCACHE_DIR=""` 时，export 为 `CCACHE_DIR=""` → ccache 使用 XDG 默认路径 `~/.cache/ccache`，但 GitHub cache action 保存的是 `/home/runner/.ccache` → 两者不匹配。

修复：diy-part2.sh 使用三层保护 — ① 顶部 export CCACHE_DIR；② defconfig 前 `./scripts/kconfig-tool --set-str CCACHE_DIR "/home/runner/.ccache"`；③ defconfig 后强制 `--enable CCACHE` + `--set-str CCACHE_DIR`，确保路径始终与 cache action 一致。
### 为什么需要 PROVIDES 虚拟包？

BINARY 包被禁用（`.config` 中设为 not set）后，如果有其他编译的包 `depends on` 这个 BINARY 包，make 会报依赖断裂错误。`package/custom-provides/Makefile` 编译一个空包，通过 OpenWrt 的 PROVIDES 机制声明它提供所有 BINARY 包名。编译期依赖系统检查到该虚拟包已启用（`CONFIG_PACKAGE_custom-binary-provides=y`），就会认为 BINARY 包已存在，不再报错。实际运行时，BINARY 包通过开机 `opkg install --force-depends` 安装到系统中。
### gh-bin 二进制兼容性检查做什么？

`download_gh_binary()` 解压 tar.gz 提取 ELF 后自动调用 `check_gh_binary_deps()`：
- 架构必须为 x86-64 或 i386（其他架构 `exit 1` 阻断构建）
- x86-64 glibc 动态链接 → `exit 1` 阻断（64 位 musl 环境无法运行 glibc）
- i386 glibc 动态链接 → 允许通过（依赖 32 位 glibc 兼容层兜底）
- 打印 NEEDED 共享库清单，提醒确保在固件的 64 位或 32 位 lib 路径中存在
